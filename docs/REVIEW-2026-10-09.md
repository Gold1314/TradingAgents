# TradingAgents fork review and Jev evaluation (2026-10-09)

## 1. What the project is

A fork of TauricResearch/TradingAgents v0.2.5 (upstream work by Yijia Xiao through
2026-05-31) plus this fork's additions from June 2026:

| Layer | What it is | Entry |
|---|---|---|
| Core | LangGraph pipeline: 4 tool-calling analysts -> bull/bear debate -> Research Manager (structured) -> Trader (structured) -> 3 risk debaters -> Portfolio Manager (structured 5-tier rating) -> rating parse -> memory log with deferred reflection on realised alpha | `tradingagents/graph/trading_graph.py` |
| CLI | Rich/Typer interactive runner | `cli/main.py` |
| Web ("StockAgents") | FastAPI server streaming every agent over SSE, Supabase persistence, 60-min cache, per-user quota, analytics, blueprint gate, admin toggle | `web/server.py` (1459 lines) |
| Brokers | Robinhood Trading MCP: OAuth, grounding, rating -> order, clamp, manual/auto/dry-run | `tradingagents/brokers/` |
| Mobile API v2 | HMAC dev tokens or Supabase JWT, per-user runs, per-user broker | `web/mobile/` |
| Voice | LiveKit worker, one persona per agent, reconcile with PM | `tradingagents/voice/`, `web/voice/` |
| Clients | SwiftUI iOS app (5.8k lines, 4 tests) and Expo/React Native app (8.6k lines, 0 tests) | `ios/`, `mobile-rn/` |
| Deploy | Dockerfile.web + railway.json, single replica | repo root |

## 2. Improvements, ranked

### 2.1 Security of the web layer (fix before any public deploy)

Verified by reading the code:

1. **Robinhood endpoints have no authentication.** `POST /api/robinhood/connect`,
   `GET /api/robinhood/account`, `POST /api/robinhood/orders/{run_id}`
   (`web/server.py:863-939`). Anyone who can reach the server sees the operator's
   holdings and buying power, and anyone holding a run id can place the pending
   order. `connect` is a bodyless POST, so a third-party page can trigger it.
   Fix: require the admin password header (`_require_admin`) or a v2 bearer token
   on all three, and require a JSON body on `connect`.
2. **The client chooses provider, model and debate rounds** (`RunRequest`,
   `web/server.py:119-129`, applied at 385-395). Nothing caps them, so one request
   can pick the most expensive model and many rounds. Fix: allowlist models and cap
   rounds server-side, or drop the fields from the public request.
3. **Quota is bypassable.** Client IP is the first `X-Forwarded-For` entry
   (`web/server.py:955-958`), which the client controls on Railway unless the edge
   strips it. The quota count fails open on any DB error (`web/db.py:255-257`) and
   header values are interpolated into a PostgREST `or_` filter string
   (`web/db.py:243-248`). Fix: take the last untrusted hop, fail closed, and pass
   values through the client's `.eq()` builder rather than a string.
4. **Admin password compared with `!=`** (`web/server.py:1339`, also
   `web/voice/router.py:99`). Use `hmac.compare_digest` as `_is_owner` already does.
5. **Full tracebacks are sent to the browser** (`web/server.py:698`). Log them,
   send a generic message.

Reported by the exploration pass, not independently re-verified by me:

6. Blueprint tokens and mobile dev tokens share format and fallback secret, so a
   blueprint token works as a v2 bearer token (`web/server.py:733-745`,
   `web/mobile/auth.py:104-140`).
7. v2 (mobile) runs ground on and, in auto mode, trade on the operator's shared
   broker (`web/server.py:447-453`, `658-663`).
8. Anonymous voice calls skip the daily/hourly caps and ownership checks when
   `X-Visitor-Id` is absent (`web/voice/router.py:128,155,193,285,306`), and
   `/reconcile` makes an LLM call with no auth.
9. `/api/events` accepts any JSON and writes it to the DB with no auth or rate
   limit (`web/server.py:1141-1157`); `/api/chart` has unbounded `lookback`.

### 2.2 Correctness

- Two failing tests (above).
- Cache key is only (ticker, trade_date) and ignores analysts, provider and models
  (`web/server.py:1260-1267`, `web/db.py:260-279`); tickers are not uppercased
  on write, so `aapl` misses the cache for `AAPL`.
- `main.py` still references `ta.reflect_and_remember(...)` in a comment; that
  method no longer exists. `test.py` at the repo root is a scratch script, not a test.
- `ConditionalLogic.should_continue_debate` comment says "3 rounds" but the code
  is `2 * max_debate_rounds`; the four `should_continue_<analyst>` methods are
  identical copies that differ only in two strings.
- `SignalProcessor` and `Reflector` are constructed with an LLM that
  `SignalProcessor` never uses.
- Reported, unverified: iOS starts runs on legacy `/api/runs` but places orders on
  v2, whose ownership check rejects runs without `user_id` (404); sells skip the
  clamp when the position cannot be read (`tradingagents/brokers/executor.py:184-187`).

### 2.3 Architecture and maintenance

- **`web/server.py` re-implements `TradingAgentsGraph._run_graph`** by calling the
  private `_resolve_pending_entries`, `propagator.create_initial_state`,
  `_log_state` and `process_signal` (`web/server.py:412,579-587`). Every change to
  the core run path now has to be made twice. Add one public generator on
  `TradingAgentsGraph` (for example `stream(ticker, date, asset_type)` that yields
  node updates and performs the same persistence at the end) and have both the
  CLI and the server consume it.
- **The agent/node list lives in six places**: `FIXED_NODES` and `ANALYST_DISPLAY`
  in `web/server.py`, `web/graph_topology.py`, voice personas, `web/static/index.html`,
  iOS `AgentNode.swift`, RN `agentNode.ts`. Export it once from the server
  (`/api/config` already exists) and have the clients read it.
- **Two native clients.** `mobile-rn/README` says React Native was chosen over
  SwiftUI, so `ios/` is superseded but still maintained. Delete one.
- **Schema drift.** `web/supabase_schema.sql` lacks the `events` and
  `analysis_requests` tables and the `runs.user_id` column that `web/db.py` and
  `web/voice/db.py` write, and it sits outside `supabase/migrations`. Move it into
  a migration and add the missing objects.
- **Dependencies are split three ways**: `pyproject.toml`, `web/requirements.txt`,
  and nothing for pytest. Declare `web` and `dev` optional-dependency groups in
  `pyproject.toml` so `uv sync --extra web --extra dev` reproduces the test
  environment, and make `Dockerfile.web` install from `uv.lock` instead of `pip install .`
  against `>=` pins.
- **No CI and no linter config.** A single GitHub Actions job running `uv sync`
  plus `pytest -m "not integration"` would have caught the two failures. `ruff`
  with defaults is enough.
- In-memory `RunManager` means the service only works with one replica
  (`railway.json`), and unfinished runs are never pruned (`web/server.py:199-207`).

### 2.4 Core pipeline quality (lower priority)

- Debate state is string concatenation of every turn; prompts to the risk
  debaters re-send all four reports plus the full history on every turn, which is
  the main token cost per run. Sending the Research Manager's structured plan plus
  the last two turns would cut cost with little loss.
- `parse_rating` falls back to "the first rating word anywhere in the text". With
  structured output the `**Rating**:` header is guaranteed, so the fallback only
  matters for free-text providers, where it can pick a word from the rationale.
  Acceptable, but worth a warning log when the fallback path fires.

## 3. Jev evaluation

### 3.1 What Jev is

Jev is TypeSafe AI's "System One" decision model, released into early access on
15 September 2026. It does not generate text. A request carries a `state` (string
or JSON, up to about 32k tokens of state inside a 64k request budget) and a map of
typed questions, and the response carries a typed answer per question with
calibrated probabilities. Three question types:

| Type | Returns | Example |
|---|---|---|
| Noul | probability of yes | "Is there enough evidence to act?" |
| Choice | one option plus a probability per option (max 255 options) | pick one of Buy / Overweight / Hold / Underweight / Sell |
| Score | a level on an ordered rubric plus probabilities | conviction 1-5 |

Reported characteristics: about 70-500 ms per call, $0.042 per million input
tokens with free output, no streaming, text input only, trained with RLCD
(Reinforcement Learning for Calibrated Decisions). Documented weaknesses: no
arithmetic, counting or date maths, weak multi-hop reasoning, accuracy drops with
long irrelevant context, and typed output prevents format errors, not wrong
decisions. Access is via waitlist at TypeSafe or through gateways (OpenRouter,
LiteLLM, DigitalOcean). I could not open TypeSafe's own docs from this sandbox;
the above comes from search summaries of secondary coverage and the two arXiv
papers, so confirm field names against docs before coding.

### 3.2 Where it fits this project

The pipeline is prose-first: the product is the reports and the debate. Jev
cannot replace any report-writing, debating or reflecting agent, and it cannot
produce the Trader's entry price, stop-loss or sizing. So it is not a cheaper
drop-in for any existing LLM role, and it does not fit `create_llm_client` as a
provider.

What the project lacks today is a **calibrated confidence number**. The Portfolio
Manager emits a label, `parse_rating` extracts it, and `rating_to_intent` sizes a
real-money order from the label alone (`tradingagents/brokers/executor.py:34-37`).
There is no abstain path and no way to size by conviction. That is exactly the
shape Jev is built for, and it is where I would use it:

1. **Decision gate after the Portfolio Manager (best fit).** State = instrument
   context, the four analyst reports (or their summary tables), the structured
   Research Plan, the Trader proposal and the PM's rendered decision. Questions: a
   Choice over the five ratings, a Noul "is the evidence sufficient to take a
   position today", and a Score for conviction. Store the probabilities in the run
   state and the memory log. Then let the executor downgrade to Hold when the
   top-rating probability is below a threshold, and optionally scale
   `default_order_notional` by it. This is the "selective decision under an error
   budget" use the OpenJev-RLCD paper describes, and it adds a cheap second opinion
   in front of real money. Cost per run is well under a cent.
2. **Hallucination check on the Market Analyst.** Noul "does this report state a
   price or indicator value that is not in the verified snapshot?" with state =
   report plus snapshot. The "Just Ask Jev" paper reports hallucination detection
   as a tested use. This would catch the issue that motivated
   `market_data_validator.py` before it cascades.
3. **Per-post sentiment scoring.** The Sentiment Analyst reads raw StockTwits and
   Reddit posts in an LLM. A Score question per post is faster and cheaper and
   gives an aggregate the analyst can cite. Moderate value.
4. **Outcome tagging in the memory log.** Noul "was the directional call correct"
   alongside the LLM's prose reflection. Minor.

### 3.3 Risks and what to check first

- **No finance validation exists.** Nothing published tests Jev on trading
  decisions. One third-party evaluation found Noul answers underconfident and
  Choice/Score overconfident on its data. Treat its probabilities as a hypothesis.
- **Context budget.** Full debate histories from this pipeline can exceed 32k
  tokens. Send the structured artifacts (plan, proposal, PM decision, report
  summary tables), not raw histories; Jev's own guidance is to filter first.
- **Early access and moving API.** Endpoint paths and response wrappers differ
  across gateways. Keep the client to one small module with a single
  `ask(state, questions) -> dict` function so a shape change is a one-file fix.
- **It can still be wrong.** Use it as a gate and a logged signal, never as the
  only decider.

### 3.4 Recommended experiment

The memory log already records realised raw and alpha returns per decision, so
calibration can be measured for free:

1. Add `tradingagents/decision/jev_gate.py` (one HTTP call, one function, under
   100 lines) and call it after the Portfolio Manager node when `JEV_API_KEY` is set.
2. Run in shadow mode: write the probabilities into the memory log entry and the
   saved state JSON, change nothing about orders.
3. After 30 or more resolved entries, compare the top-rating probability against
   realised alpha. If high-probability calls beat low-probability ones, wire the
   threshold into `rating_to_intent` behind a config flag and keep `dry_run` on
   until it has been watched for a while.

If calibration does not show up in that comparison, drop it. The cost of the
experiment is one small module and a waitlist signup.
